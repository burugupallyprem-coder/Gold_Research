## 2. Random benchmark — exact mechanics (and its honest limitation)
Code: `analyze.py` → `bracket_R()` and the `RANDOM_side_benchmark_holdout` block.

| your question | answer |
|---|---|
| same trade count? | **Yes** — the 330 holdout router entries, exactly. |
| same entry times? | **Yes** — identical timestamps; only the **side is coin-flipped**. |
| same stop / risk? | **Yes** — each trade's own `risk_price`; stop = entry − side·risk. |
| same holding period / exits? | **Same rule both sides**: target = RR·risk, stop = risk, hold-cap H=288 M15 bars (~3 trading days). |
| same RR? | **Yes** — by setup (FVG 2.5, NY 3.0), same for router and random. |
| same cost? | **Yes** — 0.40 round-trip both sides. |
| seeds | 1000, `np.random.default_rng(7)`. |

Result: router sim expectancy **+0.181R**; random mean **−0.087R** (p05 −0.210, p95 +0.040) →
router at the **100th percentile**. So at these exact moments, the router's *direction* is
genuinely better than a coin flip.

**The honest limitation (do not gloss over this):** the bracket sim is a **simplification of the
real engine** — it omits break-even stop moves and swing-based stops, and caps holding at 3 days.
That is why the router's expectancy under the sim (**+0.181R**) differs from the engine
(**+0.213R**). This is acceptable *for a percentile test* only because **both the router and the
random draws run through the identical simplified sim**, so the comparison is apples-to-apples. But
it is NOT the exact P&L engine. If your trader wants the gold-standard version, the correct upgrade
is to re-run the random side through `backtest/engine_final.py` itself (randomizing the signal side
per seed). I flag this as the one place I took an approximation.

## 3. Sharpe — exact definition
Code: `analyze.py` → `sharpe()` and `metrics_block()`.

- **Router Sharpe** = `mean(daily) / std(daily) * sqrt(252)`, **risk-free = 0**, where `daily` is
  the **realized-R-by-exit-day** series: for each calendar day, sum `0.01 × R` over trades that
  **exited** that day; days with no exit = 0.
- **Hindsight Sharpe** is **weekly** × `sqrt(52)` (labelled as such, never mixed with the daily one).
- **Buy-and-hold Sharpe** = daily **close-to-close return** × `sqrt(252)` (mark-to-market).

**Honest caveat you should know:** the router Sharpe (realized-by-exit-day) and the buy-and-hold
Sharpe (mark-to-market) are **not on the same basis** — the router doesn't mark open positions daily,
which tends to *understate* its volatility. So treat the Sharpe comparison as indicative, and lean on
the **return** comparison, which is basis-independent and unambiguous: holdout **router +95.2%** vs
**buy-and-hold +109.8%**. Buy-and-hold wins on the clean metric too.

## 4. Buy-and-hold — exactly how it's defined
Code: `analyze.py` → `BUY_HOLD_gold` block. Definition string is in `verification.json`.

- **Daily close pct-change, full compounding.** `(1+ret).prod()−1`.
- **No leverage, no vol-targeting, no cash drag, no transaction cost.** It is the pure passive
  benchmark — deliberately *generous* to buy-and-hold (zero cost), so beating it is a high bar.
- **Same windows as the router:** selection `[2019-02-20, 2024-01-01)` (start = router's first trade
  date), holdout `[2024-01-01, 2026-07-01)`. Exact bounds printed in `verification.json`.
- Numbers: selection **+54.1% / Sharpe 0.661**; holdout **+109.8% / Sharpe 1.546**.

(Note: giving buy-and-hold zero cost/slippage while charging the router 0.40/round-trip biases the
comparison *toward* buy-and-hold. Even so, the honest conclusion is that the router loses — which is
the point, not a thing to sand off.)

## 5. Momentum / direction layer — no-lookahead proof
Code: `analyze.py` → `daily_side_raw_and_shifted()`.

- `allowed_side = sign(pos_dir).shift(1)` — the side used on day *D* comes from the daily bar that
  **closed on D−1**. 12-month momentum is `px/px.shift(252)−1` (all past); EMAs are causal
  `ewm(adjust=False)`.
- **Machine-checked sample** (from `verification.json`): entry day **2019-02-19** used the daily bar
  from **2019-02-18**; `equals_sign_of_prior_posdir = true`. Same for the next samples. The code
  literally looks up `raw.index < entry_day` and confirms the used side equals the sign of the
  **strictly-prior** day's `pos_dir`.
- Intraday entries additionally come from `engine_final.py`, whose signals are causal (proven by the
  repo's own `tests/parity_final.py`).

If any same-day daily info had leaked, `side_source_daily_bar` would equal the entry day. It never does.

## 6. Hindsight strategy — isolation proof (no leak into the router)
Code: `analyze.py`. Order and data-flow matter, so here is the structural argument:

1. The **router** is built and fully scored **first** (`router`, `HONEST_ROUTER`, gate, equity)
   using only `t["agree"] = (side == allowed_side.shift(1))`. It never reads any hindsight object.
2. The **hindsight** block runs **afterward**, and only **reads**: the daily trend return stream and
   the router trades' realized R **grouped by setup** into weekly buckets, then takes the weekly
   `max`. It **writes nothing back** to `router` or to any router metric.
3. Therefore the hindsight "cheat" cannot contaminate the honest number. You can verify by deleting
   the entire hindsight block — the router/gate/benchmark outputs are byte-identical.

What the hindsight *does* cheat on (by design): choosing "whichever component won this week" needs
that week's realized result. That is why it posts weekly Sharpe **5.37** and **+8,705%** vs an honest
average component weekly Sharpe of **0.81**. It is the control that shows how a leaked/curve-fit
combination *would* look — so you can recognise the shape.
